# Case Study — 기존 솔루션은 어떻게 동작하는가

목적: 기능 나열이 아니라 **동작 원리 해부**. 각 제품이 데이터를 어떻게 받고, 어떤 구성요소가 어떤 순서로 판단하며, 사람이 어디서 개입하고, 그 구조 때문에 무엇을 구조적으로 못 하는지를 1차 자료(기술 블로그·특허·공식 문서·정부 보고서)로 적는다. 공개 자료가 없으면 "없음"을 결과로 기록한다.

## 조사 대상 (세대별)
| 세대 | 대상 | 비중 | 근거 종류 |
|---|---|---|---|
| 경비 시스템 내장 감사 | SAP Concur Verify / Detect(Oversight) · AppZen · Oversight · (Emburse 보조) | 핵심 | 교육 과정 문서, 특허, API 스키마, 조달 문서 |
| 룰 기반 감사분석 | ACL / Diligent HighBond · (IDEA·Arbutus·Alessa 묶음) · 미국 정부 감사 보고서(GAO·SSA·DOI·TIGTA) · 영국 정부 경비 탐지기 | 핵심 | 공식 테스트 목록, 1차 감사 보고서, 알고리즘 투명성 기록 |
| 카드 발급사 통제 | Ramp · (Brex 보조) · 비즈플레이·고위드·더존 | 중간 | 블로그·문서 / 국내는 마케팅뿐 |
| 유사 도메인 정석 | Stripe Radar | 참고 | 공식 엔지니어링 글 |
| LLM 챗봇 | 이전 팀 방식 + 2023~24 시도 | 한 장 | 사례·논문 |
제외: Navan·Expensify·Rydoo(Concur·AppZen과 구조 동일), 카드사 FDS(도난 탐지, 문제 다름), 은행 AML(규모 다름).

## 각 제품의 목차 (공통 틀)
1. **한 줄 정의** — 누가, 어떤 흐름 안에서, 무엇을 자동화하나
2. **데이터 입력** — 어디서 들어오나(카드사 피드·경비 제출·영수증 이미지·ERP), 어떤 전처리, **없으면 못 돌아가는 전제**
3. **구성요소와 흐름** — 룰 엔진 / 모델 / OCR / 리뷰 큐 / 피드백 저장소가 어떤 순서로 데이터를 넘기나 (그림 1장)
4. **판단 방식** — 룰과 모델의 역할 분담, 점수·등급이 어떻게 나오나, 설명은 어떻게 만드나, 사람은 어디서 개입하나
5. **피드백** — 사람의 결정이 어디로 돌아가나(모델·룰·둘 다·안 돌아감)
6. **검증·수치** — 공개된 성능 수치와 그 출처(벤더 주장 / 제3자 / 정부 실측 구분)
7. **구조적 한계** — 위 구조 때문에 **원리상** 못 하는 것. "있는데도 왜 여전히 문제인가"
8. **우리에게 주는 것** — 가져올 패턴 / 피할 함정
9. **출처** — 1차 자료 URL, 확인 수준 표시
