# 피처 엔지니어링 설계 — 2026-10-31

## 한 줄
피처는 "열 N개"가 아니라 **엔티티 × 시간창 × 집계**의 조합으로 선언하고, 거래 행에는 "이 거래 값 / 그 엔티티의 평소"라는 **비율·백분위**를 붙이며, 모든 집계는 **거래 시각 이전 데이터로만**(시점 기준) 계산한다.

## 근거 (확인된 것만)
- Airbnb Chronon(오픈소스): 키(엔티티) × 시간창 × 집계 연산으로 피처를 선언, 학습 데이터 생성 시 시점 기준(point-in-time) 조인. https://www.zenml.io/mlops-database/airbnb-bighead-chronon-feature-engineering-framework-for-consistent-onlineoffline-computation-with-temporal-point-in-tim
- Tecton·Airbnb 공저: 시간창 집계 타일링과 시점 기준 정확성. https://towardsdatascience.com/real-time-aggregation-features-for-machine-learning-part-2-fe9fd42522c0/
- Stripe 공식: 피처 엔지니어링이 Radar 개선의 최대 지렛대, velocity류 집계 피처 사용. 시간창·구현은 비공개. https://stripe.com/blog/how-we-built-it-stripe-radar (Stripe 피처 플랫폼이 Chronon 기반이라는 것은 제3자 글)
- Ramp: 피처 시스템 공개 자료 없음. 근거로 쓰지 말 것.

## 세 축
| 축 | 값 |
|---|---|
| 엔티티 | emp_id, dept, merchant, account×mcc, emp×merchant, approver |
| 시간창 | all, 30d, 7d, same_day |
| 집계 | count, sum, median, ratio(predicate), count_distinct, since_last |
이름 규약: `{entity}__{window}__{agg}` 예) `user__30d__night_ratio`, `merchant__all__distinct_users`

## 원칙
1. **비율로 본다.** 금액 자체 대신 `금액 / 본인 중앙값`, `부서 내 백분위`. 직급·부서별 기준을 모델이 따로 배울 필요가 없어진다.
2. **시점 기준.** 집계는 해당 거래 시각 이전 데이터만, 거래 자신은 제외. 위반 시 평가가 부풀려지고 운영에서 떨어진다(누수).
3. **관측 수를 피처로.** 데이터가 3개월뿐이라 초기 거래는 "평소"가 없다. `user__all__n_tx`를 넣어 비율 피처의 신뢰도를 모델이 알게 한다(콜드 스타트).
4. **선언으로 관리.** `features/catalog.yaml`에 선언, 실행기 하나가 SQL 생성. 규칙 카탈로그와 같은 패턴. 모델 manifest에 피처 카탈로그 버전 기록.
5. **규칙 결과는 넣지 않는다.** 규칙별 걸림 여부·걸린 규칙 수·검토자 정보 제외. 규칙 점수는 별도 열로 저장하고 모델 입력이 아닌 최종 앙상블에서만 합친다(docs/MODEL.md).
6. **같은 숫자를 세 곳에서.** 엔티티 통계표(`entity_stats`)를 모델, 검토 화면의 동료 비교, 선례 유사도가 공유한다. 화면의 "평소의 18배"와 모델이 본 18배가 같아야 한다.

## 예시 (#11012 노래방 590,000원)
원본: 03-20 22:57 · 47452 · CL-GLNQJ2 · 미르노래연습장 · 노래방 · 590,000 · 의욕관리비 · 증빙 N · 휴가 Y
피처: 본인 중앙값 대비 18.15배 · 심야 비율 34.5% · 부서 백분위 98.5 · 이 가맹점 쓰는 직원 1명 · 직전 간격 157분 · 같은 날 지역 2 · 시각 22 · 증빙 0 · 휴가 1

## 2차 피처: 텍스트 임베딩
가맹점명·적요 같은 글자를 뜻이 비슷하면 가까운 숫자가 되도록 벡터로 바꿔 열로 넣는다(국내 리전 임베딩 모델). 트리 모델의 실질적 약점(고차원 텍스트)을 모델 교체 없이 보완한다.
- 개선: 키워드 목록의 빈틈("미니 써큘레이터", "에어팟")을 뜻으로 잡음 / 업종코드가 뭉뚱그려진 가맹점의 이름 정보 활용 / 적요가 비슷한 거래 군집 → 발굴 루프 입구.
- 유지: 규칙의 키워드 목록은 그대로(규칙은 단어로 설명해야 함). 임베딩은 모델 쪽 보완.
- 시점: 1차 피처가 돌아간 뒤. 라벨 수만 건·텍스트 비중 확인 후에도 점수 부품만 교체하면 되도록 구조 유지.

## Radar 아키텍처(DNN·다중 가지·risk insights)와의 대조
원칙(피처가 지렛대, 판단마다 이유, 지속 재학습)은 채택, 아키텍처는 보류. 이유: 라벨 규모(수백만/일 vs 수천/년), 배치 vs 100ms, 징계 근거 수준의 설명 요구. 표 형태 소규모 데이터에서는 트리 모델이 우세(Grinsztajn et al. 2022). "모델이 스스로 패턴 발굴"은 사람이 승인하는 규칙 발굴 루프로 대체. 재검토 시점: 판정 라벨 수만 건 + 실시간 차단 요구.

## 검증
- 누수: 시간을 섞어 학습했을 때 성능이 비정상적으로 높으면 누수.
- 중복: 상관 ≥0.95 쌍은 하나만.
- 단조성: `금액/본인 중앙값`이 커질수록 위반 확률이 올라가야 함.

## 확장
새 소스(출입기록, 영수증)는 엔티티·집계 한 줄 추가. LangGraph에서는 실행기가 노드 하나.

## 구현 기록 (2026-11-01, catalog v1)
- 파일: `features/catalog.yaml`(선언 35개 = agg 25 + column 9 + history 1), `features/executor.py`, `scripts/build_features.py`, `scripts/validate_features.py`, `tests/test_features.py`. 결과 `tx_features` 30,284행 × 34열(0.8초), `entity_stats` 뷰.
- DuckDB 2.0 프로브: 윈도 `quantile_cont`, `count(distinct)`, `RANGE BETWEEN … AND INTERVAL 1 MICROSECOND PRECEDING`, 30d RANGE 하한 모두 지원. 윈도 vs 상관 서브쿼리 3만 행 불일치 0.
- 시점 기준 구현: 윈도 프레임 상한 `INTERVAL 1 MICROSECOND PRECEDING`(자신·동시각 제외). `since_last_min`은 두 전략 모두 상관 서브쿼리(동시각 제외 일관성). 상관 전략은 큰 파티션(직급)에서 O(n²)라 검증용 표본 500건에만 사용.
- 설계 조정: 직급 백분위 → 중앙값 배수(비용). `lookahead: true` 명시(same_day 4개, until_next). 이력 그룹(`hist__`)은 기본 제외, `--with-history`에서만(약한 라벨 누설). 선례 유사도는 제외(자기 규칙 집합의 함수).
- 검증 7종 전부 통과. 발견: `user__30d__n_tx`≈`user__all__n_tx`(r=0.997, 3개월 데이터) → known_redundant로 유지. `merchant__all__n_distinct_users`는 "적을수록 의심" 가정이 약한 신호와 반대(+0.36): 금지 업종 규칙이 걸리는 술집이 인기 가맹점이라서. 방향 기대 제거, 실제 판정 후 재검토.
- #11012 시점 기준 값: 본인 중앙값 대비 14.53배(전 기간 18.15), 심야 비율 25%, 부서 18.09배, 의욕관리비×노래방 과거 1건(백분위 100), 이 가맹점 과거 사용자 0, 직전 간격 157분, 같은 날 지역 2. 화면 동료 비교가 이제 이 값을 읽는다(`service.peer_from_features`, `point_in_time=True`).
