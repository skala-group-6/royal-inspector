# 규칙 개선 루프와 무작위 표본 — 2026-10-31

## 왜 필요한가 (출발점)
규칙 엔진은 거래를 두 더미로 나눈다. **걸린 더미**(규칙 중 하나라도 반응, 현재 약 29%)와 **안 걸린 더미**(어떤 규칙도 반응 없음, 약 71%).
윤경팀은 걸린 더미만 본다. 안 걸린 더미는 "이상 없음으로 확인된" 것이 아니라 **아무도 안 본** 것이다.

## 필터는 두 방향으로 틀린다
| | 잘못 잡음 | 놓침 |
|---|---|---|
| 상황 | 걸렸는데 정상 | 안 걸렸는데 위반 |
| 발견 | 자연히 됨(검토 중 "아님") | 안 됨. 아무도 안 보므로 겉으로 드러나지 않으면 영원히 모름 |
| 운영상 위험 | — | 잘못 잡음만 보이므로 모두 임계치를 조이는 방향으로만 가고, 시스템이 "조용해지는" 것을 "좋아지는" 것으로 착각 |

## 놓침을 보는 유일한 창문: 무작위 표본
안 걸린 더미에서 **제비뽑기**로 일부를 꺼내 검토 목록에 섞는다. 사람이 고르면 그것도 또 하나의 규칙이라 선입견 밖은 여전히 안 보이므로 무작위여야 한다.
- 검토 목록 = 걸린 더미 (100−p)% + 안 걸린 더미 무작위 p%. 각 건에 "규칙 / 무작위" 출처 표시. p는 옵션(출발점 10~20%, 무작위에서 위반 0건이 지속되면 줄임, 0은 권하지 않음).
- 무작위 n건 중 위반 k건 → 안 걸린 더미 전체의 위반 비율 추정 → "규칙이 얼마나 덮고 있는가"를 처음으로 숫자로 말할 수 있음.
- 무작위는 프롬프팅(질문하기 화면)과 무관하다. 기간별 검토 목록을 만들 때만 섞인다.
- 같은 표본이 세 역할을 한다: 새 패턴 발굴의 입구 / 규칙 재현율 측정 / 모델의 중립 시험지(docs/MODEL.md).

## 루프
```
규칙 N개로 전수 검사
  → 검토 목록 (걸린 것 + 무작위 표본)
  → 윤경팀 판정
  → 무작위 쪽에서 "위반"이 나왔나?
       아니오 → 규칙 N개 유지, 다음 기간
       예 (1건부터) → 발굴: 그 거래의 공통점 → LLM이 패턴명·설명·규칙 초안 제안
              → 검증: 초안을 과거 데이터 전체에 소급 실행(몇 건 걸리나, 기존 규칙과 겹침, 이미 판정된 건과 일치하나, 합성 정답셋 유지)
              → 승격: 윤경팀 승인 시 catalog에 규칙 N+1 등록(버전↑, 출처='발굴')
  → 규칙 N+1개로 계속 (무작위 표본은 유지)
```
- **제안은 1건부터.** 우리 규모에서 "몇 건 모이면"은 반년이 걸린다. 모으는 일은 사람이 아니라 소급 실행이 한다: 초안을 과거 전체에 돌려 "추가 0건"이면 일회성으로 거절, "37건 추가·기판정 5건 중 4건 위반"이면 승인. 소급 결과 없는 제안은 화면에 올리지 않는다.
- "처음으로 돌아가는" 것이 아니라 규칙이 하나 늘어난 채로 계속 돈다. 이미 판정된 거래는 다시 판정하지 않는다.
- 새 규칙은 **직후 소급 + 다음 기간부터 상시** 둘 다 적용된다. 소급 실행은 몇 초이며 그 자체가 검증 단계다. 소급에서 새로 걸린 거래만 검토 목록에 추가된다.
- 자동으로 바뀌는 것은 모델 점수뿐. 규칙과 임계치는 항상 사람이 바꾼다.

## 범인 관점 변형 (라벨 없이 할 수 있는 발굴) — 선택 기능, 팀 워크숍 후 착수
Stripe 공식 글 기준 대조: Stripe도 "과거 공격을 범인 입장에서 복기 → 흔적 → 피처 → 백테스팅"이라는 사람의 절차를 쓴다. 합성 주입·레드팀은 공식 자료에 없다. 우리는 실제 사례가 22건뿐이라 "규칙을 알면 어떻게 피할까"를 상상해 재료를 보충하는 점만 다르다.
수정 원칙 4가지: ① 숫자에 "우리가 가정한 회피 방법 중"이라는 꼬리표 ② 변형을 세 칸으로(잡음 / 잡을 수 있음→후보 / 잡을 수 없음=카드 데이터에 흔적 없음, 솔직히 기록) ③ 후보는 기존 피처로 이미 구분되는지 확인 후 추가(Stripe의 '효과 없던 피처' 교훈) ④ 실제 사례 입력 문(화면에서 한 줄 추가)을 함께 연다.
화면: "규칙 점검" 한 장 — 꼬리표 달린 숫자, 세 칸 표, [검토]→소급 결과·기존 피처 중복 여부·기판정 일치, [+ 사례 추가]. 변형 합성 거래는 모델 학습·평가에 절대 포함하지 않는다(is_synthetic).
사례마다 "이 규칙을 알면 어떻게 피할까"를 물어 회피 변형을 만들고, 변형을 합성 거래로 심어 규칙 엔진이 잡는지 시험한다. 안 잡힌 변형이 남기는 흔적을 잡는 숫자가 피처·규칙 후보가 된다.
```
① 사례 → 변형 생성 (LLM 초안, 사람이 다듬음) → cases.yaml variants: [{설명, 남기는 흔적, 필요한 데이터}]
② 변형 → 합성 주입 → 규칙 엔진 → 잡힘/안 잡힘 = 커버리지 지도 ("알려진 회피 N개 중 M개 탐지")
③ 안 잡힌 변형의 흔적 → 피처 후보(모델용 숫자 열) / 선을 그을 수 있으면 규칙 후보
④ 실데이터 소급 실행(너무 드물거나 너무 흔하면 기각) + 판정과 대조 → 사람이 승인 → 카탈로그 등록
```
예: 사례 17(12분 간격 2회, R03이 잡음) → 변형 "하루 간격 분할"(R03 60분 창이 못 잡음) → 흔적 "같은 가맹점 7일 합계" → 실데이터 분포 확인 → 승인 시 피처/규칙.
- 변형 합성은 **커버리지 시험용**이지 학습용이 아니다(순환 방지).
- 변형 커버리지는 규칙·임계치를 바꿀 때마다 재측정한다("오탐을 줄였더니 변형 3개를 새로 놓친다"가 보임).
- 운영 후 무작위 표본에서 나온 새 위반은 사례 23으로 추가되어 같은 네 단계를 탄다. 윤경팀이 아는 실제 수법이 들어오면 변형의 질이 올라간다.

## 구현 상태 (2026-11-01)
입구 1(무작위 표본)과 입구 2(모델 고점수)는 `queue` 테이블로 가동 중: `scripts/build_queue.py --from --to` → 규칙 행 + 모델 상위 M(기본 20) + 무작위 p%(기본 10%, 최소 10건), 각 행에 `queue_source`·`selection_prob`·시드·파라미터 기록. 미플래그 행의 판정은 `rule_id NULL`로 저장되어 tx 단위 라벨이 되고, Home의 출처별 표가 "무작위 n건 중 위반 k건 → 미플래그 위반율 추정"을 보여준다. 재빌드는 판정이 있으면 `--force`에서만, 판정된 행은 유지.

## 새 규칙의 네 입구
1. 무작위 표본에서 윤경팀이 "위반" → 가장 확실한 발견, 첫 번째 근거 거래
2. 모델 점수는 높은데 걸린 규칙이 없는 거래 → 규칙과 다른 눈이 본 것
3. 검토자가 "아님"을 같은 사유로 반복 → 반대 방향의 억제 규칙 후보
4. 범인 관점 변형에서 규칙이 못 잡은 것 → 지금 당장, 라벨 없이 가능한 유일한 입구
