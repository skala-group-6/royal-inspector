# 제품의 본질과 Claude-native 설계 방향 (2026-11-03)

## 한 문장
**거래 데이터를 넣으면, 사람이 봐야 할 것을 골라 순서대로 내놓고, 사람의 판정을 기억해서 다음 달 더 잘 고르는 제품.**

## 네 박자
1. **넣는다** — 엑셀 → "누가·언제·얼마·어디서·어느 부서"로 정리.
2. **고른다** — 규칙이 규정 위반을, 모델이 평소와 다른 것을, 무작위가 둘 다 놓친 것을 큐에.
3. **판정한다** — 사람이 근거를 보고 위반/아님/보류. 한 건 2분.
4. **기억한다** — 판정이 라벨이 되어 순서를 고치고, 반복 패턴은 새 규칙으로 승격.

하지 않는 것: 위반을 기계가 확정 · 원천에 없는 정보(누구와·왜) 생성 · 사용자에게 코드 작성 강요.

## 비교
| | Hex | Retool | 우리 |
|---|---|---|---|
| 한 줄 | 물으면 답하는 노트북 | 조립하면 화면이 되는 빌더 | 넣으면 볼 것이 나오고, 보면 똑똑해지는 검토 엔진 |
| 데이터 수용 | 사람이 설명을 쓰고 LLM이 읽음(이해 아님) | 아무 테이블, 판단 없음 | 계약(행ID·주체·시각 + 선택 열) + 매핑 |
| 판단 | 없음 | 없음 | 규칙 + 모델 + 사람 |
| 행 단위 판정·큐·기한 | 없음 | 조립해야 함 | 내장 |
| 피드백 | 설명문 보강(재학습 없음) | 없음 | 라벨 → 재학습, 규칙 승격 |
Retool·Hex 위에 우리를 만들 수는 있으나 그들이 해주는 것은 화면 한 겹. 상세 `docs/TOOLING_DECISION.md`, `research_notes/hex_product_structure.md`.

## "어떤 데이터셋이든"의 범위
- 엔진이 요구하는 최소: **행 ID, 주체, 시각.** 금액·분류·부서는 있으면 피처가 늘고 없으면 그 피처만 빠짐.
- 적용 가능: 사람이 행 단위로 판정해야 하는 모든 표(출장비, 구매 발주, 보험 청구, 신고 검토).
- 표에 없는 것: **무엇이 이상한가.** 그것은 규정 문서에 있다. → 데이터 + 규정 → 규칙 초안을 만드는 입구가 필요(아래).

## Claude-native 설계 원칙 (Claude Code의 원칙을 옮김)
| 원칙 | 우리 | 상태 |
|---|---|---|
| 파일이 상태다 | 규칙·피처·라벨·임계치 = YAML+SQL, git | ✅ |
| CLI가 유일한 표면, 사람과 에이전트가 같은 명령 | 적재~큐 전부 CLI, 화면은 창 | ✅ |
| 검사가 매 변경을 지킨다 | Octave 체크 4종 | ✅ |
| 에이전트는 초안, 사람은 승인 | 규칙 초안·컬럼 매핑·근거 문장은 에이전트, 등록·실행·**판정**은 사람 | 🔧 (새 규칙 승인 화면 예정) |
| 컨텍스트 파일 | 카탈로그 explain·policy_ref, 규정 원문, 판정 사유 | 🔧 |
| 스킬 | "규칙 추가", "임계치 조정", "사용자 조사", "새 팩 만들기" | ⬜ |
| MCP로 도구 노출 | 서비스 함수를 MCP 서버로 | ⬜ |
**고정선**: 판정 버튼은 에이전트가 누르지 않는다.

## UX로 본 두 단계
**지금(법카 팩)**: 엑셀 올림 → 검토 화면에 순서대로 → 한 건 클릭하면 근거 세 줄 → 위반/아님/보류, J로 다음 → 월말 요약 → 규칙 화면에서 숫자만 수정. 코드 없음.
**나중(새 팩)**: 출장비 엑셀 + 규정 PDF 올림 → 에이전트가 팩 초안(컬럼 매핑, 규칙 후보, 피처 선언, 합성 사례) + 과거 데이터 백테스트 건수 제시 → 사람이 체크해 승인 → 다음 달부터 같은 화면에 탭 추가. 사람이 한 일은 파일 올리기와 체크.

## ML의 위치
- 팩마다 **따로** 자라고, **방법과 코드는 하나**(피처 실행기·라벨 빌더·학습·기준선 게이트).
- 라벨 없음 → 임시 라벨로 학습, 기준선 못 이김, 화면은 기준선 순서(현재). 판정 수백 건 → 재학습 → 기준선 넘으면 화면 순서 교체. 무작위 표본의 "위반"이 규칙 너머를 배우는 재료.
- 윤경팀이 ML에 할 일: 판정만. 요약에 "모델 v3, 라벨 n건, 기준선 대비 +x%" 한 줄.
- 새 팩은 모델도 처음부터. 도메인 간 전이 없음.

## 계획에 미치는 영향
- 계획 1의 "입력 계약"을 **팩 규격**(폴더 구성: 매핑·규칙 SQL·피처 선언·합성 사례·규정 문서)으로 넓혀 문서화. 에이전트가 두 번째 팩을 쓸 때 따르는 양식.
- 계획 10에 **팩 생성 에이전트**(데이터 + 규정 → 초안 → 백테스트 → 승인) 추가. 자연어 질의와 같은 묶음. 법카 팩이 윤경팀 손에서 돌아간 뒤.
