# 데이터 적재 — 파일이 정식 입구, 연동은 조건부 (2026-11-04)

## 한 줄
**엑셀 올리기를 최후의 보루가 아니라 정식 입구로 만든다.** 카드사 직접 연동은 하지 않는다. 사내 DB 연결은 조건(§2)이 생기면 "읽기" 한 칸만 추가한다.

비유: 우리 제품은 서류 받는 창구다. (1) 잘못된 서류는 창구에서 돌려보내고, (2) 받은 서류는 서랍에 모아 매번 전체를 다시 정리하고, (3) 창구를 화면에 두고, (4) 나중에 서류 대신 직접 받아 와도 정리 방식은 그대로다.

## 1. 왜 연동이 먼저가 아닌가

### 1.1 BI 툴과 입력 상황이 다르다
| | BI 툴(Tableau·Power BI·Hex) | 감사 분석(ACL·MindBridge) | 우리 |
|---|---|---|---|
| 고객 | 수천 곳, 원천 제각각 | 감사 대상마다 다름 | **사내 배포 1곳** |
| 데이터 상태 | 이미 웨어하우스에 정리됨 | 은행·ERP에서 내려받은 파일 | 사내 시스템을 합친 엑셀 |
| 갱신 | 매일·매시간 | 감사 주기 | **월 1회** |
| 입구 | 커넥터 먼저 | **파일이 1급**. ACL은 `IMPORT EXCEL`이 표준(`case_study/04` §2). MindBridge는 파일 업로드가 기본이고, 직접 커넥터는 QuickBooks·Sage Intacct·Xero 3종뿐이며 SAP는 파일 가이드만 있음 | 파일 |

연동을 전제로 한 제품(Concur Detect·AppZen·Oversight·비즈플레이)은 연동 밖 데이터를 못 받는 것이 공통 한계다(`case_study/03` §7, `case_study/08` §7).

### 1.2 카드사 데이터만으로는 규칙 19개 중 4개
카드사가 아는 것은 카드번호·승인일시·가맹점(명·주소 일부)·업종·금액·승인/취소다. 규칙이 **거를 때** 쓰는 열 기준(근거 표시용 열은 제외):

| 필요한 원천 | 규칙 | 수 |
|---|---|---|
| 카드 데이터 + 카드 소유자 | R03 분할결제 · R04 선결제 · R08 제한업종 · R09 유류 과다 | 4 |
| + 경비정산(적요·첨부·계정) | R06(적요 + 직원 명부) · R10 · R16 · R21 | 4 |
| + 인사·근태·출장·주소 | R01 · R02 · R05 · R07 · R11 · R13 · R14 · R15 · R17 · R18 | 10 |
| + 출입기록 | R12 | 1 |

지금 받는 거래 엑셀은 한 행에 SAP전표번호·정산유형·계정·첨부·휴가여부·출장·주거지 주소가 다 들어 있다. **사내 여러 시스템을 이미 합쳐 뽑은 추출본**이다. 진짜 원천은 카드사가 아니라 고객사 내부다. 카드사에서 직접 받으면 이 열들을 잃는다.

### 1.3 국내 카드사 연동 경로
| 경로 | 내용 | 우리에게 |
|---|---|---|
| 표준 피드(미국 Visa VCF·Mastercard CDF3) | 발급 은행이 설정하면 경비 시스템이 파일·API로 받음 | **국내에 같은 표준 없음** |
| 카드사 EDI 중계 | 카드사별 계약. 비즈플레이는 17개 카드사와 EDI, 실시간 제공은 10개사 | 카드사마다 계약·형식이 다르고, §1.2의 열이 없음 |
| 스크래핑 중개(CODEF 등) | 카드사 사이트 인증으로 수집. 연동 시점 이후 내역만, 새벽 배치, 카드사별 승인/취소 반영 차이가 있다는 안내 있음(네이버웍스 도움말, 본문 직접 확인 못 함 ⚠️) | 과거 데이터로 학습하는 구조와 안 맞음 |
| 기업 공공 마이데이터 | 국세청 등 **행정정보**를 금융사에 제공(KB국민카드 2026-08, IBK 2026-10 도입) | 카드 사용 내역 아님. 해당 없음 |
| 여신금융협회 매출거래정보 API | **가맹점 매출** 조회용 | 지출(법인카드 사용) 쪽이 아님. 해당 없음 |

실시간이라는 장점도 쓸 자리가 없다. 우리는 월 단위 사후 검토이고, 카드사 차단은 범위 밖이다(`PROJECT_NOTES.md` §8).

### 1.4 사내 DB 직접 연결 — 방향은 맞지만 지금은 아님
- 장점: 사람 손을 안 탐, 열 이름 안정, 누락 적음.
- 비용: 원천이 SAP·경비정산·인사·근태·출입보안 4~5개이고, 각각 보안 심사·읽기 전용 계정·망 연결 승인이 필요하다. 주소·휴가·출입은 개인정보라 승인이 길다. 엑셀은 윤경팀이 이미 가진 권한 안에서 움직인다.
- 이득: 월 1회라 자동화로 아끼는 시간은 한 달에 몇 분이다.
- 요구사항서도 "카드사·ERP 시스템 직접 연동(엑셀 업로드로 대체)"를 범위 밖으로 둔다(`deliverables/01_요구사항서.md`).

## 2. 연동을 다시 검토할 조건
| 이런 일이 생기면 | 붙일 것 |
|---|---|
| 점검 주기가 월 → 주·일 | 사내 DB·데이터웨어하우스 읽기 전용 SQL 추출 |
| 엑셀을 만드는 사람이 매달 손으로 합치고, 거기서 오류가 남 | 위와 같음. 합치는 일을 SQL로 |
| 두 번째 고객사(SaaS화) | ERP 커넥터(SAP·더존). 카드사는 중계사(비즈플레이류) 경유로 가장 나중 |

어느 경우든 §3.1 덕분에 바꾸는 것은 "읽기" 한 칸이다.

## 3. 만들 것 — 네 가지

### 3.1 읽기와 바꾸기 분리 (나중에 갈아끼우기)
지금 `scripts/load.py`는 읽기·열 이름·변환·취소 처리가 한 파일에 섞여 있고, 원천 열 이름(`"SAP전표번호"`, `"총금액"`)과 열 이름 줄 위치(`header=1`)가 코드에 박혀 있다. 이를 둘로 나눈다.

| 단계 | 하는 일 | 원천이 바뀌면 |
|---|---|---|
| ① 읽기 | 엑셀 → 원천 열 이름 그대로의 표 | 이것만 추가(예: SQL로 같은 열 뽑기) |
| ② 바꾸기 | 매핑표로 표준 열(`PACK_SPEC.md` §3)로, 금액·날짜·Y/N 변환, 취소 짝짓기, 계정 매핑 | 그대로 |

### 3.2 입구 검사 (잘못된 파일은 바로 거절)
**열 이름 줄은 자동으로 찾는다.** 거래 엑셀은 첫 줄이 `EXPENSE 정보`라는 제목이고 둘째 줄이 열 이름이다. 출입기록은 첫 줄이 열 이름이다. 위에서 10줄을 훑어 매핑표의 이름과 가장 많이 겹치는 줄을 열 이름 줄로 잡는다. 못 찾을 때만 화면에서 사용자가 고른다.

**매핑표는 팩 파일로 한 번 정한다.** 매달 묻지 않는다.
```yaml
# packs/corp_card/mapping.yaml (예시)
transactions:
  sheet: 비용점검
  columns:
    총금액:   { to: total,    type: won }       # "₩1,200" → 1200
    거래일:   { to: tx_date,  type: date }
    휴가여부: { to: is_leave, type: yn }        # Y → true
```
열 이름이 바뀌면(예: `총금액` → `합계금액`) 거절하고 "총금액에 해당하는 열을 골라 주세요"라고 묻는다. 고르면 별명으로 저장되고 다음 달부터는 자동이다. 별명 추가는 매핑표 변경이므로 기록이 남는다.

**검사 항목** (결과는 통과 / 경고 / 거절)
| 항목 | 결과 | 이유 |
|---|---|---|
| 필수 열(`tx_id` 키 재료·`emp_id`·시각) 없음 | 거절 | 엔진이 못 돈다 |
| 날짜·금액을 못 읽은 값 비율이 기준 초과 | 거절 | 형식이 바뀐 신호 |
| 날짜가 선택한 기간 밖 | 경고 | 잘못된 파일일 수 있음 |
| 행 수가 직전 대비 급변 | 경고 | 일부만 뽑혔을 수 있음 |
| **처음 보는 계정** | 경고(목록 표시) | 계정 매칭은 지금 `load.py` 안의 수동 사전이다(현재 원천 계정 49개: 자동 37·수동 10·규정 없음 2). 매칭이 안 된 계정의 거래는 R11·R13·R16·R17에서 **알림 없이 빠진다** |
| 권장 열 비어 있음(주소·업종 등) | 경고 | 해당 규칙·피처가 꺼진다 |

### 3.3 파일 보관함 + 전체 재생성 (지난달 데이터 보존)
올린 파일을 버리지 않고 보관함에 쌓는다. DuckDB는 **매번 보관함 전체로 다시 만든다.** 새 달 데이터를 덧붙이지 않는다.
- 부분 취소가 다음 달 파일에 오면 지난달 원거래와 짝지어야 한다(`load.py` §2가 같은 사람·가맹점·가까운 날짜로 연결). 달마다 따로 넣으면 짝이 끊긴다.
- "DuckDB는 재생성 가능"이라는 원칙(`STORAGE_ARCHITECTURE.md` §1)을 그대로 지킨다. 연 30만 건이면 수 초 규모다.

**기간이 겹치면 날짜 구간 단위로 최근 업로드가 이긴다.** 3월 파일을 고쳐 다시 올리거나 1~3월 누적본을 올려도, 겹치는 날짜는 가장 최근 파일 것만 쓴다. 그래서 누적본·월별본 어느 쪽이 와도 같은 결과가 나온다. 행 단위 중복 제거는 하지 않는다. 같은 날·같은 가맹점·같은 금액의 진짜 두 건이 실제로 있고, `keys.det_ids`가 이를 출현 순번으로 구분하므로 행 비교로는 "중복"과 "진짜 두 건"을 가를 수 없다.

**교체 전 검사**
- 새 DB는 `warehouse_next.duckdb`에 만들고, §3.2 검사와 행 수 확인을 통과해야 교체한다. 실패하면 기존 DB가 그대로 남는다.
- **이미 판정된 거래(`reviews`)의 tx_id가 새 DB에 없으면 교체를 멈추고 목록을 보여 준다.** 판정이 존재하지 않는 거래를 가리키는 사고를 막는다. 원천에서 금액이 수정된 거래는 `tx_id` 재료(`total` 포함)가 바뀌어 여기서 걸린다(§5).

보관함 파일은 원본과 같은 민감도다. 서버 디스크에 두고 백업 대상에 넣는다(`STORAGE_ARCHITECTURE.md` §5 "원본 엑셀 보관"). 누가·언제·무엇을 올렸고 결과가 어땠는지는 사람의 기록이므로 Postgres `loads` 테이블에 둔다.

### 3.4 업로드 화면
```
① 파일 끌어놓기 + 기간 선택
② 서버가 §3.2 검사 → 미리보기 ("3월 거래 2,431건 · 취소 제외 52건 · 경고: 처음 보는 계정 2개")
③ [적재] → 뒤에서 재생성: 적재 → 규칙 → 피처 → 점수 → 큐, 진행 상태 표시
④ §3.3 교체 전 검사 통과 → 교체 → 검토 화면에 새 기간
```
`API.md` §4의 함수와 대응: 검사·미리보기 `ingest`, 확정 `confirm_load`, 진행 `get_load`, 열 고르기 `get_column_mapping`, 품질 `get_quality`. 한 번에 하나만 돌도록 잠근다. FastAPI(ROADMAP 계획 3)가 있어야 한다.

## 4. 순서와 완료 기준
순서는 **3.1 → 3.2 → 3.3 → 3.4.** 3.1·3.2는 API 없이 지금 착수할 수 있다. 3.3의 판정 대조는 계획 3 전에는 DuckDB `reviews`를, 이후에는 Postgres를 읽는다.

| 단계 | 완료 기준 |
|---|---|
| 3.1 + 3.2 | 새 적재기로 만든 표준 테이블이 현재 `load.py` 결과와 **행·열 단위로 동일**(회귀 테스트) |
| 3.2 | 망가뜨린 파일(열 빠짐·이름 바뀜·제목 줄 추가·처음 보는 계정·날짜 형식 변경)이 각각 정해진 이유로 거절 또는 경고 |
| 3.3 | 월별 파일을 차례로 올린 결과 = 같은 기간 누적본 한 번 올린 결과. 같은 기간 재업로드 시 최신 파일만 반영 |
| 3.3 | 판정된 거래가 빠진 파일을 올리면 교체가 멈추고 기존 DB 유지 |
| 3.4 | 화면에서 올린 결과 = CLI로 같은 파일을 적재한 결과 |

## 5. 열린 질문
- 윤경팀이 매달 받는 파일이 누적본인지 월별본인지. 설계는 둘 다 처리하지만 실제 형태로 3.3 테스트를 돌려야 한다.
- 운영 파일이 테스트 파일과 같은 모양인지, 인사·근태 결합을 매달 누가 하는지. 결합이 수작업이면 §2 두 번째 조건에 해당한다.
- 원천에서 수정된 거래(금액 정정 등)를 같은 거래로 볼지. 지금 키로는 새 거래가 된다. 원천 식별자(전표번호+승인번호)만으로 키를 만들 수 있는지 실데이터로 확인이 필요하다.
