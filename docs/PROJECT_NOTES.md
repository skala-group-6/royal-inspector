# 법인카드 점검 서비스 — 프로젝트 노트

작성일 2026-10-31. 지금까지의 조사·데이터 확인·설계 결정을 한 곳에 모은 문서. 리서치 원문은 `reports/법인카드 감사 솔루션 분석.md`(git 미추적), 데이터 프로파일은 `data/inventory/`.

## 1. 문제

- 윤리경영팀이 연 약 30만 건 법인카드 거래를 수작업(12MM)으로 점검한다.
- 점검 대상: 사적 사용(개인 물품, 휴일·휴가 사용, 선결제·분할결제, 거주지 인근, 동시간 다른 장소), 리더 점검(출장지 밖 사용, 골프·유흥 업무 연관성, 과다 주유), 절차 위반(증빙 누락, 허위 증빙, 계정 오류, 타인 카드 대여).
- 원하는 것: 거래 엑셀 업로드 → 자연어 또는 사전 명령으로 점검 → 시나리오별 적발과 근거 → 신규 패턴 발굴 → 증빙 OCR 대조 → 증빙 위변조 분석.

## 2. 기존 솔루션 조사 결론

- 이 범위를 통째로 제공하는 제품은 없다. 글로벌 경비감사(AppZen, Oversight, Concur)는 자사 흐름 안의 거래만 감사하고 엑셀 사후 감사 모드가 없다. 국내 SaaS(비즈플레이, 고위드, 더존)는 전표·정산 도구다.
- 전통 CAAT 룰 플래그의 확정률은 10~47%, 비지도 ML 정밀도는 9~20%. "LLM이 새 패턴을 발굴한다"는 측정된 근거가 없다.
- 한계의 뿌리는 알고리즘이 아니라 데이터 층(좌표·사업자번호·표준 업종코드 부재, PG 가맹점명)과 워크플로 층(플래그를 증거 없이 닫는 검토 단계)이다.
- 최근 국내 적발 사례는 전부 단순 룰(주말 사용, 50만원 쪼개기)로 잡히는 패턴이었다.

## 3. 설계 원칙

**판정은 코드가, 번역과 서술은 LLM이, 우선순위는 모델이.**

| 층 | 역할 | 학습 여부 |
|---|---|---|
| 1 적재·정규화 | 카드사 엑셀을 표준 스키마로, HR·출입·규정 데이터 결합 | 없음 |
| 2 규칙 엔진 | 시나리오당 규칙 1개, 출력 계약 고정(규칙ID, 걸린 필드, 임계치, 관련 거래, 근거) | 없음 |
| 3 우선순위 모델 | 플래그 재정렬. 피처=규칙 출력, 라벨=검토자 결정 | 지도학습(라벨 축적 후) |
| 4 자연어 | 질문 → 시나리오+파라미터 번역. 제한된 text-to-SQL은 쿼리 노출 후 실행 | 없음(골든셋 평가) |
| 5 증빙 | OCR → 승인번호·금액·날짜 대조. 포렌식은 결정적(해시, PDF 리비전, 산술)과 확률적(ELA, AI 판별)으로 분리 | 없음 |
| 6 신규 패턴 | LLM이 규칙 초안 제안 → 과거 데이터 백테스트 → 사람 승인 | 없음 |
| 7 검토 워크플로 | 케이스 화면, 결정과 사유 필수 저장(=라벨) | - |
| 8 평가 하네스 | 위반 주입 합성셋, 자연어 골든셋, 검토 확정률 | - |

UX와 모델 개발은 2층의 출력 계약을 먼저 합의하면 병렬 진행 가능.

## 4. 데이터 확인 결과 (data/raw 2개 파일)

## 5. 모델(로지스틱/XGBoost)의 자리

- 역할: 규칙에 걸린 플래그의 "확정 확률"로 재정렬. 플래그 생성, 취소 제거, OCR, 자연어 번역에는 쓰지 않음.
- 피처: 규칙 출력 열(휴일, 거리, 반복 횟수, 업종, 증빙, 과거 플래그 수, 동료 대비 배수).
- 라벨: 검토 화면의 "위반/아님" 결정. 보류는 제외.
- 조건: 시나리오별 양성 수십 건, 전체 수천 건. 시간순 분할, 상위 K건 확정률로 평가.
- 이번 범위에서 실제 라벨은 없음. 선택지: (a) 모델 자리와 라벨 수집 장치만 설계, (b) 징계사례 22건을 심어 학습 시연(실제 성능 아님을 명시).

## 6. 부가 제공 요소(탐지 아님)
사람·부서별 지출 프로필과 동료 비교, 월별 급변 지점, 승인자 프로필(전부 승인, 요청자와 거주지 근접), 가맹점 집중도, 부서별 증빙 첨부율·심야·휴일 비율, 입력 품질 리포트.

## 7. 결정 기록 (2026-10-31 오후)
- **Streamlit 유지.** 정식 프런트는 (a) 화면 구조가 두 번 연속 체험에서 안 바뀌거나 (b) 다중 사용자로 DuckDB 잠금이 문제될 때 착수. 버려지는 것은 Streamlit 파일뿐, 서비스 함수·문장 템플릿·화면 사양(`docs/REVIEW_SCREEN.md`)은 남는다.
- **임계치는 규정이 아니라 도구 설정.** 개발팀이 초기값을 정하고 윤경팀이 확정. 설정은 `rules/catalog.yaml` 한 곳, 변경은 버전과 사유 기록.
- **검토 화면은 지금 라벨 수집 장치가 아니라 측정 장치.** 개발팀 판정은 reviewer 이름으로 구분해 학습·선례에서 제외. 윤경팀 판정만 라벨.
- **모델은 시연용(합성 라벨)과 운영용(윤경팀 라벨)을 같은 스크립트로.** 라벨 출처는 인자로 강제, 시연 시 한계 문구 필수. `docs/MODEL.md`.
- **선례 기능.** 징계사례 22건과 미래의 판정 거래를 같은 테이블·함수·카드로. 비교 열쇠는 규칙 서명(구조적), 자연어는 표시용. `docs/PRECEDENTS.md`.
- **UI 기준은 Stripe Radar·Ramp.** 3가지 판정, 문장형 이유+근거 규정, 2단계 심각도, 긴 꼬리 접기, 기각 시에만 사유. 조사: `research_notes/audit_review_ui_references*.md`.
- **근거 인용 원칙.** 회사 이름(Stripe, Ramp 등)을 설계 근거로 댈 때는 공개 1차 자료를 먼저 확인한다. 2026-10-31 피처 구조 논의에서 Ramp는 공개 자료가 없어 근거에서 제외했고, 구조의 근거는 Airbnb Chronon·Tecton 공개 문서로 바꿨다(docs/FEATURES.md).

## 8. 결정 기록 (2026-11-03)
- **제품 정의 = 범용 검토 엔진 + 법인카드 팩.** 코드 점검 결과 엔진(규칙·피처 실행기, 라벨, 모델, 큐, 판정, 서비스)은 이미 데이터 무관하고, 법카 전용은 적재·합성·규칙 내용·서비스 4줄뿐. 다시 만들지 않고 폴더 경계와 입력 계약(6열)만 선언한다. 범용 빌더(Retool류) 자체 개발은 하지 않는다 — `docs/TOOLING_DECISION.md`.
- **화면은 윤경팀이 쓰는 4개만(검토·요약·큐·규칙).** 적재·피처·모델·재학습은 CLI와 문서, 요약 화면에 상태 한 줄.
- **React + FastAPI 착수.** 2026-10-31의 "Streamlit 유지" 조건 중 (b) 잠금 문제가 반복돼 조건 충족. FastAPI 서버가 DuckDB 쓰기를 독점.
- **사례 조사 교훈은 ROADMAP 백로그 A~N.** 금액 가중 우선순위·자동 종결·닫힌 카탈로그는 채택하지 않음.
- **카드사 데이터는 주 재료, 카드사 차단은 범위 밖.** 네 정보(가맹점·업종·금액·일시/위치)로 직접 보이는 것은 룰, 쌓아서 보이는 것은 피처·모델, 없는 것(누가·왜)은 출입·HR 보강 후 사람 확정.
- **Streamlit 기능 동결(2026-11-03).** `app/Home.py`, `app/pages/`에는 새 기능을 넣지 않는다. 버그 수정만. React 검토 화면이 실데이터로 동작하면 삭제. 서비스 함수 변경은 두 화면 모두 깨지지 않게 테스트로 확인.
