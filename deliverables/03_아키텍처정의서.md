# 아키텍처 정의서 — 법인카드 사용 점검 지원 시스템

문서 버전 0.1 (2026-11-01). 요구사항 ID는 `01_요구사항서.md` 참조.

## 1. 설계 원칙
1. **판정은 코드가, 번역과 서술은 LLM이, 우선순위는 모델이.** 규칙 엔진이 결정적으로 판정 후보를 만들고, LLM은 자연어를 규칙 호출로 바꾸고 결과를 서술하며, 모델은 순서만 정한다.
2. **사람이 바꾸는 것과 기계가 바꾸는 것을 분리.** 규칙·임계치·새 규칙 등록은 사람 승인 필수. 기계가 혼자 바꾸는 것은 검토 순서뿐.
3. **출력 계약 고정.** 규칙 엔진의 출력(rule_id, evidence, related_tx_ids, severity, rule_version)이 모든 상위 층의 입력. 모델·OCR·LLM이 바뀌어도 이 계약은 유지.
4. **같은 숫자를 여러 곳에서.** 엔티티 통계는 화면의 동료 비교, 선례 유사도, 모델 피처가 공유한다.
5. **재현 가능.** 원본 불변, 스크립트 재실행 시 동일 결과, 버전·해시 기록.

## 2. 전체 구조 (레벨 0)

```
 ① 적재 ─→ ② 규칙 엔진 ─→ ③ 피처·라벨 ─→ ④ 점수 모델 ─→ ⑤ 검토 큐 ─→ ⑥ 사람 판정
                ▲   ▲                ▲                                      │
     임계치 확정 ┘   │                │ 되먹임1: 판정 → 라벨 → 재학습 ◀──────────┘
     새 규칙 승인 ───┘                │ 되먹임2: 과거 점검 결과 → 라벨
        ▲                            
        └── 되먹임3: 무작위 표본·회피 변형에서 놓친 것 → 새 규칙 후보
 ───────────────────────── DuckDB 단일 파일 (모든 상자가 읽고 씀) ─────────────────────────
```
단계별 시각화: `docs/architecture/level0.html`

### 2.1 엔진과 팩 (2026-11-03)
위 ①~⑥ 중 ①의 적재 스크립트와 ②의 규칙 내용만 데이터 의존이고, 나머지는 거래형 데이터 공통이다.

| | 범용 엔진 | 법인카드 팩 (`packs/corp_card/` 예정) |
|---|---|---|
| 코드 | `scripts/run_rules.py`, `features/executor.py`, `scripts/labels.py`, `models/`, `scripts/train.py`, `scripts/score_tx.py`, `scripts/build_queue.py`, `app/service.py`(출입 타임라인 4줄 제외), 테스트 | `scripts/load.py`, `scripts/synth.py`, `synth/cases.yaml`, `rules/sql/*.sql`, `rules/catalog.yaml` 내용, `features/catalog.yaml` 내용, `labels/weak.yaml` 내용, 출입·HR 대조 |
| 입력 계약 | `tx_active` 최소 6열(tx_id, emp_id, tx_ts, total, mcc_name, dept) + 선택 보강 테이블 | 엑셀 2개 → 계약 테이블 생성 |
| 화면 | 검토·요약·큐·규칙 4개. flags/queue/reviews/tx_score만 읽음 | 규칙 이름·증거 문장은 카탈로그에서 옴 |

두 번째 팩(예: 출장비 정산)은 적재 스크립트와 규칙·피처 선언만 새로 쓴다. 엔진·화면·API는 그대로.

## 3. 구성요소
| # | 구성요소 | 역할 | 입력 → 출력 | 구현 | 기술 선택 이유 |
|---|---|---|---|---|---|
| ① | 적재·정규화 | 엑셀을 표준 테이블로. 금액 숫자화, 취소 처리, 계정 매핑, 출입 연결 | 엑셀 2개 → transactions, employees, access_logs, policy_accounts | `scripts/load.py` | DuckDB: 설치 없음, 엑셀 직접 읽기, 3만~30만 건에 수 초, SQL로 규칙 작성 용이 |
| ② | 규칙 엔진 | 규칙 21개 전수 실행, 근거·관련 거래·등급 기록 | tx_active → flags | `rules/catalog.yaml`, `rules/sql/*.sql`, `scripts/run_rules.py` | 규칙=SQL 파일 1개, 임계치=카탈로그 한 곳. 설명 가능성과 버전 관리 |
| ③ | 피처·라벨 | 거래를 평소 대비 숫자로(피처), 규칙 투표로 임시 정답(라벨) | tx_active, flags → tx_features, labels | `features/catalog.yaml`, `scripts/features.py`, `scripts/labels.py` (예정) | 엔티티×시간창×집계 선언, 시점 기준 계산(feature store 표준). 규칙 결과는 피처에서 제외(순환 방지) |
| ④ | 점수 모델 | 규격(fit/predict/explain)에 맞는 후보를 같은 시험에 올려 1등 채택 | tx_features, labels → tx_score, manifest | `models/` (예정) | 표 데이터·소규모 라벨에서 트리 모델 우세. 규격 분리로 DNN 등 교체 가능 |
| ⑤ | 검토 큐 | 걸린 거래 점수순 + 안 걸린 거래 무작위 표본, 출처 기록 | flags, tx_score → 목록 | `app/service.list_flags` (무작위 표본 예정) | 규칙이 놓치는 것을 보는 유일한 창문 |
| ⑥ | 사람 판정 | 케이스 화면, 위반/아님/보류, 이력 보존 | 목록 → reviews | `app/service.py`, `app/pages/` (Streamlit) | 임시 UI. 서비스 함수는 정식 프런트(React+FastAPI)로 그대로 이전 |
| ⑦ | 선례 | 징계사례·과거 판정을 규칙 서명 유사도로 제시 | precedents, flags → 유사 사례 | `scripts/load_precedents.py`, `service.get_precedents` | 구조적 키(규칙 집합)로 비교해 "왜 비슷한가" 설명 가능 |
| ⑧ | 개선 루프 | 무작위 표본·회피 변형·반복 사유 → 규칙 후보 → 소급 검증 → 승인 | reviews, 변형 → candidate_patterns → catalog | `synth/cases.yaml` variants, 승인 UI (예정) | 제안은 1건부터, 승인은 사람, 등록은 기존 규칙과 동일 통로 |
| ⑨ | 자연어 질의 | 질문 → 규칙 ID+파라미터(1차), 제한 SQL(2차) | 문장 → list_flags 호출 | 예정 | LLM은 번역만, 계산은 코드 |
| ⑩ | 증빙 파이프라인 | OCR 추출 → 승인번호·금액 대조 → 결정적/확률적 위변조 신호 | 파일 → 대조 결과 | 예정 | 한국어 영수증 OCR(CLOVA/Upstage), 결정적 신호 우선 |

## 4. 데이터 흐름
1. 엑셀 업로드 → ① → `transactions`(원본 열 + 정규화 열 + exclude_reason), `access_logs`, `policy_accounts`
2. ② 전수 실행 → `flags` (거래당 규칙별 1행)
3. ③ 전수 계산 → `tx_features`(거래당 1행), `labels`(출처 표시)
4. ④ 학습·점수 → `tx_score`, `models/<v>/manifest.json`
5. ⑤ 목록 생성 → 화면. 각 건에 `queue_source`(rule / random / model)
6. ⑥ 판정 → `reviews` (append-only, superseded_by)
7. 되먹임: `reviews` → `labels`(재학습) / `precedents`(kind=review) / `candidate_patterns`(놓침) → 승인 → `rules/catalog.yaml` 버전↑

## 5. 사람 개입 지점
| 지점 | 누가 | 무엇 | 시스템 반영 |
|---|---|---|---|
| 판정 | 감사자 | 위반/아님/보류 + 사유 | reviews → 라벨, 적중률, 선례 |
| 임계치 확정 | 관리자 | 규칙 파라미터 값 | catalog 버전↑, 전수 재실행 |
| 새 규칙 승인 | 관리자 | 후보 승인/거절/수정 | catalog 등록, 소급 실행, 상시 적용 |
| 과거 결과 입력 | 관리자 | 점검 이력 엑셀 | labels(import) → 재학습 |

## 6. 기술 스택
| 층 | 선택 | 대안과 전환 시점 |
|---|---|---|
| 저장 | **Postgres**(reviews·queue·ui_events·사용자·규칙 변경 이력 = 사람의 기록) + **DuckDB**(거래·flags·피처·점수 = 재생성 가능한 계산). 2026-11-03 확정 전 분석 `docs/STORAGE_ARCHITECTURE.md` | DuckDB 파일은 배치가 새 파일에 쓰고 교체, 서버는 읽기 전용 |
| 규칙 | SQL + YAML 카탈로그 | — |
| 피처·모델 | pandas, scikit-learn, XGBoost | 라벨 ≥1만·양성 ≥1천 시 DNN 후보 활성 |
| 텍스트 | 국내 리전 임베딩(2차 피처) | — |
| LLM | 국내 리전(Bedrock 서울) 또는 사내 모델. 마스킹된 최소 필드만 | — |
| UI | React(Vite + shadcn/ui + TanStack) + FastAPI (2026-11-03 확정, `web/`) | Streamlit은 PM 검증·시연용으로 유지. 로우코드 빌더 불채택: `docs/TOOLING_DECISION.md` |
| DB 소유 | FastAPI 서버는 DuckDB를 읽기 전용으로 열고 Postgres에 쓴다. 배치는 `warehouse_next.duckdb`에 쓰고 원자적 교체 | DuckDB는 쓰기 프로세스 1개만 허용 |
| 오케스트레이션 | 스크립트 순차 실행 | LangGraph: ①~⑧이 노드, 표본 비율·임계치·규칙 버전이 상태, 판정·승인이 인터럽트 |
| 검증 | pytest + Octave check | 합성 재현율 100%, 서비스·선례 테스트 |

## 7. 보안·개인정보
- 이름은 화면에서 마스킹, 주소·사번은 역할별 노출.
- LLM·OCR·지오코딩 외부 호출 시 마스킹된 최소 필드만 전송, 국내 리전 우선.
- 모든 조회·수정은 로그(ui_events, reviews).
- 개발팀 테스트 판정은 reviewer 이름으로 분리, 학습·선례 제외.

## 8. 비기능 설계
| 항목 | 설계 |
|---|---|
| 재현성 | 원본 불변, 스크립트 멱등, 데이터 스냅샷 해시, 규칙·피처·모델 버전 |
| 성능 | 3만 건 규칙 전수 수 초, 30만 건 분 단위 |
| 확장 | 규칙 추가=SQL 1파일+카탈로그 1항목, 피처 추가=선언 1줄, 모델 교체=플러그 1파일 |
| 장애 | 단계별 스크립트 독립 실행, 실패 시 이전 테이블 유지 |

## 9. 미결 사항
- 지오코딩 API 키(R05·R06·R12 정밀도)
- 영수증 파일과 거래의 연결 키
- 윤리경영팀 과거 점검 결과 보유 여부
- 임계치 확정 주체와 주기
- **tx_id 결정적 키 교체**(현재 행 순번 → 전표·승인번호 또는 해시). Postgres 판정이 거래를 안정적으로 가리키기 위한 선결 과제
- 로그인 방식(시연: 이름 선택 / 배포: 인증) 과 reviewer 화이트리스트
- LLM 외부 전송 범위(규칙 출력 필드만 vs 로컬 모델) — 윤경팀 확인 필요
- 배포 위치(윤경팀 PC vs 사내 서버). 클라우드는 데이터 반출로 제외
